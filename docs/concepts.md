# Trustica – Core Concepts

This document defines the fundamental concepts used throughout the Trustica project.
All design decisions, implementations, and extensions must align with the definitions provided here.

---

## Environment

An **Environment** is a logical trust domain that defines how TLS certificate trust is established for a specific runtime or tool ecosystem.

An environment is **not**:
- A binary
- A command
- A process
- A package manager

An environment represents a conceptual boundary where trust rules apply.

### Examples of Environments

- OpenSSL (system-level usage)
- Python (certifi-based trust)
- Node.js
- Git
- JVM

---

## Trust Target

A **Trust Target** is an environment that provides a complete strategy for configuring and validating certificate trust.

Each trust target must define:
1. **Detection** – How to determine whether the environment exists
2. **Application** – How to install or activate the CA certificate
3. **Verification** – How to confirm that trust is working correctly

A trust target encapsulates all environment-specific knowledge.

---

## Adapter

An **Adapter** is a concrete implementation of a trust target.

Adapters:
- Implement environment-specific behavior
- Fulfill the Detect / Apply / Verify contract
- Are isolated from each other
- Are replaceable

Adapters must not:
- Communicate with other adapters
- Modify OS-level trust stores
- Maintain global state

---

## Core

The **Core** is the central orchestration layer of Trustica.

The Core:
- Coordinates trust operations
- Manages execution flow
- Tracks environment states
- Aggregates results

The Core does not:
- Know implementation details of environments
- Interact directly with the operating system
- Execute external commands

---

## Registry

The **Registry** is a declarative catalog of known environments.

Responsibilities:
- Declare which environments Trustica supports
- Provide adapters to the Core

The Registry does not:
- Perform detection
- Apply certificates
- Execute verification

---

## Detection

**Detection** determines whether an environment is present and applicable on the current system.

Detection:
- Is environment-specific
- Must be safe and non-destructive
- Does not modify system state

Detection answers the question:
> “Can this environment be configured here?”

---

## Application

**Application** installs or activates a CA certificate within an environment.

Application:
- Must be idempotent
- Must not duplicate certificates
- Must not corrupt existing configuration

Application answers the question:
> “How does this environment trust a CA?”

---

## Verification

**Verification** confirms that trust has been successfully applied.

Verification:
- Must be explicit
- Must reflect real TLS behavior
- Must fail if trust is not working

Verification answers the question:
> “Does TLS validation succeed using this environment?”

---

## Environment State

Each environment progresses through explicit states:

- **NotDetected**  
  The environment is not present or not applicable.

- **Detected**  
  The environment exists and can be configured.

- **Applied**  
  Trust configuration was applied successfully.

- **AlreadyTrusted**  
  The CA certificate was already trusted.

- **Failed**  
  An error occurred during detection, application, or verification.

- **Skipped**  
  The environment was intentionally ignored.

State transitions are controlled exclusively by the Core.

---

## Trust Plan

A **Trust Plan** is an execution plan generated by the Core.

It defines:
- Which environments will be processed
- Which operations will be performed
- The order of execution

The plan is derived from detection results and user input.

---

## Result

A **Result** represents the outcome of a trust operation for a single environment.

A result includes:
- Environment identifier
- Final state
- Optional error details

Results are aggregated and reported to the user.

---

## Idempotency

**Idempotency** means that applying the same operation multiple times produces the same outcome without side effects.

Trustica enforces idempotency at the environment level.

Running Trustica repeatedly must not:
- Duplicate certificates
- Break existing configurations
- Produce inconsistent results

---

## Isolation

Each environment is processed independently.

Failures:
- Do not propagate to other environments
- Do not abort the overall execution
- Are reported individually

---

## Scope Boundaries

Trustica explicitly operates **outside** the following scopes:

- Operating system trust stores
- Network interception or proxying
- Browser trust configuration
- Automatic certificate discovery

These boundaries are enforced at the architectural level.

---

## Summary

Trustica’s conceptual model is built around:
- Explicit trust domains
- Clear responsibility boundaries
- Predictable, verifiable behavior

This shared vocabulary ensures consistency across design, implementation, and AI-assisted development.

## Core Domain Types

### 1. Environment State (Enum)

The lifecycle state of an environment during execution.

```
EnvironmentState
├── NotDetected    // Environment not present on this system
├── Detected       // Environment exists, ready to configure
├── Applied        // Certificate was installed successfully
├── AlreadyTrusted // Certificate was already trusted
├── Verified       // Trust confirmed working (post-apply)
├── Failed         // Error occurred
└── Skipped        // Intentionally ignored (user flag or config)
```

---

### 2. Environment (Value Object)

Identifies a logical trust domain.

```
Environment
├── ID          string   // "openssl", "python", "nodejs", "git"
└── Name        string   // "OpenSSL", "Python (certifi)", "Node.js", "Git"
```

---

### 3. Result (Value Object)

Outcome of processing one environment.

```
Result
├── Environment   Environment
├── State         EnvironmentState
├── Message       string           // Human-readable detail (optional)
└── Error         error            // If State == Failed
```

---

### 4. Trust Plan (Value Object)

Execution plan built after detection.

```
TrustPlan
├── Targets       []Environment    // Environments to process
└── Skipped       []Environment    // Environments that won't be processed
```

---

### 5. Certificate (Value Object)

The CA certificate to be trusted.

```
Certificate
├── Path          string           // Filesystem path to PEM file
└── Content       []byte           // Raw PEM content (loaded)
```

---

## Port Interfaces (Contracts)

### 1. EnvironmentPort

What the Core expects from every environment adapter.

```
EnvironmentPort
├── ID()              → Environment
├── Detect(ctx)       → (bool, error)        // Is this environment present?
├── Apply(ctx, cert)  → (State, error)       // Install the certificate
└── Verify(ctx)       → error                // Confirm trust works
```

---

### 2. SystemPort

Abstraction over host system interactions. Adapters depend on this, Core does not.

```
SystemPort
├── FileExists(path)           → bool
├── ReadFile(path)             → ([]byte, error)
├── WriteFile(path, data)      → error
├── AppendToFile(path, data)   → error
├── GetEnv(key)                → string
├── SetEnv(key, value)         → error
├── RunCommand(cmd, args...)   → (output, error)
└── HomeDir()                  → string
```

---

### 3. Registry

Catalog of available adapters.

```
Registry
└── All()   → []EnvironmentPort
```

---

## Core Orchestrator

The brain that coordinates everything.

```
Orchestrator
├── registry       Registry
│
├── Detect(ctx, cert)           → TrustPlan
├── Apply(ctx, cert, plan)      → []Result
├── Verify(ctx, results)        → []Result
└── Run(ctx, cert)              → []Result   // Full flow: detect → apply → verify
```

## Questions Before Coding

1. **Error granularity** — Should `Result.Error` be a custom error type with codes (e.g., `ErrPermissionDenied`, `ErrFileNotFound`), or is `error` enough for MVP?

2. **Context usage** — Should `Detect`, `Apply`, `Verify` accept `context.Context` for cancellation/timeouts from day one?

3. **Certificate validation** — Should `Certificate` validate it's a valid PEM on load, or defer to adapters?

4. **Verification strategy** — Each adapter verifies differently. Should there be a common `VerificationTarget` (e.g., a URL to test against), or is that per-environment?
